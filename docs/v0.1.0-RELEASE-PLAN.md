# ChasteAI v0.1.0 — Release Plan

> **Status:** Approved for implementation
> **Target:** First stable release

---

## 1. Executive Summary

ChasteAI is an open-source AI customer support infrastructure platform. The codebase has solid architectural foundations but suffers from:

- **Critical bugs** that make the product non-functional end-to-end (setup wizard creates orphan workspace, SQLite compatibility broken, null-pointer crashes)
- **Non-functional stubs** and prematurely added features that inflate complexity without delivering value (Baileys WhatsApp, Slack/Discord webhooks, empty worker services)
- **Duplicated code** and stale legacy files that confuse development
- **Hardcoded assumptions** that break provider agnosticism (OpenAI-only embeddings)

### v0.1.0 Goal

Ship a **stable, single-tenant, self-hostable** AI customer support platform where:

1. A company sets up one instance (via `pnpm setup`)
2. Creates one AI agent with one workspace (shared by team members)
3. customers can interact with the agent via:
   - Embedded web widget (iframe)
   - Telegram
   - WhatsApp Business API
4. The AI works with any OpenAI-compatible provider (OpenAI, Groq, Together AI, etc.)
5. RAG/knowledge base works when the provider supports embeddings; cleanly disabled otherwise

## 2. Key Architecture Decisions

### 2.1 Single-Workspace Per Instance

| Decision                                                      | Rationale                                                                                               |
| ------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------- |
| Each instance has exactly **one workspace**                   | Eliminates ~40% of routing complexity (membership checks, workspace switching, workspace CRUD)          |
| All users share the same workspace                            | Simplifies onboarding: first user creates workspace during setup, subsequent users are approved into it |
| Role model simplified to `admin` / `member`                   | No owner/admin/member distinction needed for single-workspace                                           |
| `memberships` table becomes simpler (user + workspace + role) | Only two possible roles, no workspace switching                                                         |
| Workspace CRUD pages removed from dashboard                   | One workspace, no need to list/switch/create                                                            |

**Files affected:** All tRPC routers, dashboard layout, sidebar navigation, workspace pages, auth actions, setup wizard.

### 2.2 WhatsApp Strategy

| Decision                                                             | Rationale                                                                 |
| -------------------------------------------------------------------- | ------------------------------------------------------------------------- |
| Remove `@whiskeysockets/baileys` dependency                          | Reverse-engineered protocol, against ToS, unreliable, non-functional      |
| Implement **WhatsApp Business API (Cloud API)** as provider          | Official Meta API, production-ready, REST-based, fits channel abstraction |
| Customer zero setup: company configures once, customers just message | Exactly the desired UX                                                    |
| Setup guidance in Channels UI                                        | Guide user through Meta Business verification + webhook setup             |

**WhatsApp Business API integration scope:**

- `POST /{phone-number-id}/messages` for sending (text, template, interactive)
- Webhook receiver for inbound messages
- Token-based auth (long-lived access token from Meta)
- Webhook verification (Meta's `hub.verifytoken` challenge)

### 2.3 Channel Provider Cleanup

| Decision                            | Rationale                                       |
| ----------------------------------- | ----------------------------------------------- |
| **Remove** Slack webhook stub       | Non-functional, only handles `url_verification` |
| **Remove** Discord webhook stub     | Non-functional, returns PONG for everything     |
| **Keep and fix** Telegram webhook   | Partially working, worth finishing              |
| **Implement** WhatsApp Business API | Priority channel for the product                |
| **Keep** Widget (primary channel)   | Fully functional, needs minor fixes             |

### 2.4 AI Provider & RAG

| Decision                                                      | Rationale                                                                                  |
| ------------------------------------------------------------- | ------------------------------------------------------------------------------------------ |
| Keep provider-agnostic abstraction                            | Core architectural strength                                                                |
| **Configurable embeddings provider**                          | Separate `embeddingsProvider` config on agents — can be same as chat provider or different |
| RAG auto-disabled when no embeddings provider configured      | Clear UI messaging: "Knowledge base requires an AI provider with embedding support"        |
| Fix hardcoded `text-embedding-3-small` in crawl/ingest routes | Use the configured embeddings provider instead                                             |
| Remove hardcoded `type: "openai"` in RAG retrieval            | Use the configured provider                                                                |

### 2.5 Dependency Cleanup

| Action     | Package                                | Reason                               |
| ---------- | -------------------------------------- | ------------------------------------ |
| **Remove** | `@whiskeysockets/baileys`              | Non-functional, ToS-violating        |
| **Remove** | `@slack/web-api`, `@slack/socket-mode` | No Slack implementation              |
| **Remove** | Stripe-related env vars and deps       | No billing in v0.1.0                 |
| **Remove** | Resend/SMTP deps and env vars          | No email in v0.1.0                   |
| **Keep**   | Redis in docker-compose?               | If not used by any code path, remove |
| **Keep**   | service/ stubs?                        | Remove empty dirs                    |

## 5. Success Criteria for v0.1.0

The release is ready when:

1. **Fresh install works end-to-end:**
   - `pnpm setup` runs without errors (SQLite and PostgreSQL)
   - Setup wizard completes all 5 steps
   - User lands on dashboard with their workspace and agent

2. **Chat works:**
   - Widget chat: visitor sends message, AI responds (streaming)
   - Telegram: company configures bot, customer messages, AI responds
   - WhatsApp: company configures Business API, customer messages, AI responds

3. **Agent management:**
   - Create, edit, delete agents
   - Configure provider (API key, base URL, model)
   - Set system prompt

4. **Multi-user:**
   - First user (setup) is admin
   - Subsequent signups are pending
   - Admin can approve/deny from team page
   - Approved users can access the dashboard

5. **Self-host:**
   - Works with SQLite (local) and PostgreSQL (production)
   - No external dependencies required
   - All features work offline

6. **Agent knowledge:**
   - Agents can be scoped to specific documents via `agent_documents` junction table
   - Knowledge instructions configurable per agent
   - Whitelist model: no entries = workspace-wide, entries = private

7. **Test conversations:**
   - Widget `?test=true` creates test conversations
   - Analytics exclude test conversations
   - Dashboard shows test badge and filter toggle

8. **Quality:**
   - No null-pointer crashes
   - No PostgreSQL-specific SQL in SQLite codepaths
   - No stale/legacy schema files
   - No non-functional UI elements
