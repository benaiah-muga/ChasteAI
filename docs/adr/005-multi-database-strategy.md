# ADR-005: Multi-Database Strategy (PostgreSQL + Turso/SQLite)

**Status:** Proposed

**Date:** 2026-06-25

## Context

ChasteAI must support two database modes:
1. **Production/Cloud**: PostgreSQL with pgvector extension — full power, vector search, concurrent access
2. **Local/Self-Host**: SQLite via Turso/libSQL — zero-dependency setup, single-file database, local-first

The system must detect the environment and use the appropriate database without manual configuration beyond environment variables.

## Decision

Use an **adapter-based database client** from a single `packages/db` package, backed by Drizzle ORM's multi-dialect support.

### Architecture

```
packages/db/
├── src/
│   ├── schemas/
│   │   ├── workspaces.ts
│   │   ├── users.ts
│   │   ├── agents.ts
│   │   ├── conversations.ts
│   │   ├── messages.ts
│   │   ├── documents.ts
│   │   ├── subscriptions.ts
│   │   └── analytics.ts
│   ├── client.ts           # Adapter that exports the correct db instance
│   ├── migrations/         # Shared migrations (generated by drizzle-kit)
│   └── utils.ts            # Shared helpers
├── drizzle.config.ts       # Multi-dialect config
└── package.json
```

### Client Adapter Pattern

```typescript
import { drizzle as pgDrizzle } from "drizzle-orm/node-postgres"
import { drizzle as sqliteDrizzle } from "drizzle-orm/libsql"
import { Pool } from "pg"
import { createClient } from "@libsql/client"
import * as pgSchema from "./schemas/pg"
import * as sqliteSchema from "./schemas/sqlite"

function createDatabaseClient(env: Env) {
  if (env.DATABASE_URL?.startsWith("postgres")) {
    const pool = new Pool({ connectionString: env.DATABASE_URL })
    return pgDrizzle(pool, { schema: pgSchema })
  }

  const client = createClient({
    url: env.TURSO_URL ?? "file:local.db",
    authToken: env.TURSO_AUTH_TOKEN,
  })
  return sqliteDrizzle(client, { schema: sqliteSchema })
}
```

### Handling Dialect Differences

Drizzle allows sharing ~90% of schema definitions. Differences are handled via:
- **Separate schema files** for tables that use PostgreSQL-only features (e.g., `vector` columns)
- **Conditional exports** in `client.ts` that import the correct dialect's schemas
- **Raw SQL bridge**: PostgreSQL features like `pgvector` similarity search use `sql` template tags, which throw if called against SQLite

The key insight: most of ChasteAI's schema (workspaces, users, agents, conversations, messages) is standard SQL and works identically in both dialects. Only `document_chunks.embedding` (vector column) and some analytics functions are PostgreSQL-specific.

### Vector Search in SQLite Mode

When running on SQLite, vector search degrades gracefully:
- Documents are still ingested and chunked
- Embeddings are stored as BLOB columns
- Vector search falls back to keyword + metadata filtering
- A future enhancement could use `sqlite-vec` extension

### Migration Strategy

```bash
# Generate migrations (PostgreSQL as primary)
pnpm --filter db db:generate

# Run migrations based on environment
pnpm --filter db db:migrate    # Auto-detects dialect
```

Drizzle Kit generates dialect-specific SQL. In CI, we store PostgreSQL migrations. SQLite users generate fresh migrations from the same schema.

## Consequences

### Positive

- Local development with SQLite: zero external dependencies, instant setup
- Production with PostgreSQL: full power, vector search, concurrent access
- Single `packages/db` to import regardless of deployment target
- Contributors don't need to install PostgreSQL to start contributing
- Self-host users can choose their preferred database

### Negative

- Some PostgreSQL-only features require branching logic in application code
- Schema divergence risk if not carefully managed — mitigated by CI checks that validate both dialects
- Vector search quality differs between PostgreSQL (native) and SQLite (fallback)

### Neutral

- Turso/libSQL supports Drizzle migrations natively
- Migration files must be reviewed for dialect compatibility

## Alternatives Considered

- **PostgreSQL only**: Rejected — violates self-host-first principle. Requiring PostgreSQL for local dev creates friction for solo developers and contributors.
- **SQLite only**: Rejected — not suitable for production multi-tenant workloads with concurrent writes and vector search requirements.
- **ORM-agnostic dual setup**: Using Prisma for Postgres + Drizzle for SQLite would double maintenance. Drizzle handles both well.
- **Neon serverless only**: Rejected — cloud dependency, violates self-host-first.
