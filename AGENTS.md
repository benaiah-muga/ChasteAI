# ChasteAI -- Agent Guide

## Project Overview

Open-source AI customer support infrastructure. Monorepo with Turborepo + pnpm.
Self-host first: everything must work locally with zero external dependencies.

## Architecture

- **Monorepo**: Turborepo + pnpm workspaces (6 packages)
- **Database**: PostgreSQL (production) via Drizzle ORM. SQLite/Turso (local/quick-start) via libSQL client.
- **API Layer**: tRPC (end-to-end type safety, co-located with Next.js)
- **Auth**: Auth.js v5 with Credentials provider (default) + optional OAuth (GitHub, Google)
- **AI**: Provider-agnostic strategy pattern via registry (OpenAI implemented)
- **Frontend**: Next.js 15 App Router, React 19

## Database

### Multi-Dialect Architecture

The `packages/db` package supports both PostgreSQL and SQLite (via libSQL/Turso):

- **PostgreSQL**: Used in production. Full Drizzle ORM with `pg` client. Schemas in `packages/db/src/schemas/pg/`.
- **SQLite**: Used for local development and quick start. Uses `@libsql/client`. Schemas in `packages/db/src/schemas/sqlite/`.
- **Turso**: Same as SQLite but with remote sync. Also uses `@libsql/client` with `libsql://` URLs.

The `client.ts` provides:

- `getDatabaseClient()` -- always returns the PG client (backward compat for existing app code)
- `createClientForDialect(url)` -- returns the right client for any dialect (used by setup wizard)
- `detectDialect(url)` -- detects `postgresql` vs `sqlite` from a connection string

### 16 Tables

workspaces, agents, conversations, messages, documents, document_chunks, channels, api_keys, memberships, subscriptions, analytics_events, agent_documents, user, account, session, verificationToken

Auth tables (user, account, session, verificationToken) managed by `@auth/drizzle-adapter`.
Custom `password` column on `user` table for Credentials provider.
`agent_documents` junction table for agent-scoped document assignment (whitelist model).
`DATABASE_URL` in `apps/web/.env`.

### SQLite Migration SQL

Raw migration SQL for SQLite lives at `packages/db/src/migrations-sqlite/0000_init.sql`. This is executed by the TUI setup script and is not generated by Drizzle Kit (which only produces PG migrations currently).

## Setup Flow

Setup now spans two environments:

```
TERMINAL (TUI)                          BROWSER (GUI)
pnpm setup
  |
  +-- [SQLite] -> create DB, migrate,   http://localhost:3000/setup
  |               write .env                  |
  +-- [Turso]  -> configure, migrate,         +-- Step 1: Account
                   write .env                 +-- Step 2: Database (shows TUI config)
                                              +-- Step 3: AI Provider
  User opens URL in browser                   +-- Step 4: Workspace + Agent
  after TUI completes                         +-- Step 5: Done -> /dashboard
```

### TUI script (`scripts/setup-tui.ts`)

Uses `@clack/prompts` for interactive terminal UI:

- Prompts: SQLite (local file) or Turso (edge DB)
- Creates database, runs migrations, writes `.env`
- Outputs URL to continue in browser

### GUI wizard (`apps/web/src/app/(setup)/`)

Dark-themed installer-style wizard with 5 steps:

- Step 1: Create admin account (email + password). Calls `createAccountAction` server action.
- Step 2: Shows DB config from TUI. User must click "Test Connection" — gates proceeding with `dbTest.status === "passed"`. Calls `testDbConnectionAction`.
- Step 3: Configure AI provider. Preset selector (OpenAI, Groq, NVIDIA, Together AI, Fireworks AI, DeepSeek, Mistral AI, Custom) auto-fills `baseUrl` and `model`. User enters API key. Must click "Test Connection" — gates proceeding with `providerTest.status === "passed"`. Calls `testProviderConnectionAction` which uses `createProvider` from `@chaste-ai/ai` to do a live API call via `provider.testConnection()`.
- Step 4: Create workspace + first agent (name, description, system prompt).
- Step 5: Done, redirect to dashboard via `finalizeSetupAction`.

Uses `ExpandableError` component: friendly message -> "Show details" toggle -> monospace error block with copy button.

State management: `WizardData` type holds all form fields. `TestState` type (`{ status: "idle" | "testing" | "passed" | "failed", message?, details? }`) tracks DB and provider test status separately.

## Homepage

`apps/web/src/app/page.tsx` performs first-run detection. If a user exists in the database:

- **Signed in** → redirects to `/dashboard`
- **Not signed in** → redirects to `/signin`

If no user exists (fresh install), shows the setup/launchpad prompt. This replaces the previous manual navigation flow.

## Auth

- **Strategy**: JWT (not database sessions)
- **Credentials**: Email + password, hashed with bcryptjs
- **Session expiry**: Absolute max age of 7 days by default. Configurable idle timeout (auto sign-out after inactivity) and max session length in Settings.
- **Idle timeout**: `IdleTimeoutProvider` in `apps/web/src/components/idle-timeout-provider.tsx` wraps the dashboard layout. Tracks user activity and signs out silently after configured idle minutes (default 60).
- **OAuth**: GitHub + Google -- enabled only when `AUTH_GITHUB_ID`/`AUTH_GITHUB_SECRET` or `AUTH_GOOGLE_ID`/`AUTH_GOOGLE_SECRET` are set
- **Middleware**: `apps/web/src/middleware.ts` protects dashboard routes. `/setup`, `/signin`, `/signup`, `/pending-approval`, `/` are public.
- **Pages**: `/signin`, `/signup`, and `/pending-approval` at `apps/web/src/app/(auth)/`. Full-bleed layout (no card wrapper).
- **Config**: `auth.config.ts` (edge-compatible) + `auth.ts` (full config with providers)
- **User status**: `user` table has `status` column (`"active" | "pending" | "suspended"`, default `"pending"`). First user created via signup or setup wizard gets `status: "active"`. Subsequent signups get `status: "pending"` and are redirected to `/pending-approval`.
- **Admin approval**: Pending users cannot sign in (`authorize` callback + `signinAction` both block `pending` and `suspended`). Admins approve via server actions in `apps/web/src/lib/actions/admin.ts`: `approveUserAction` (sets active + creates membership), `denyUserAction` (sets suspended). Team page at `/dashboard/team` shows pending approvals queue with workspace/role selector modal.
- **Security codes (recovery)**: Users generate a set of single-use security codes after setup (compulsory — prompt cannot be dismissed). Codes serve as a password fallback for account recovery. Sign-in form has a toggle between password and security code modes. After signing in with a security code, user is forced to change their password via `ChangePasswordModal`. Security codes are hashed with bcrypt and stored in `security_codes` table. The `changePasswordAction` in `apps/web/src/lib/actions/auth.ts` accepts security codes as the "current credential" (not just passwords). The `authorize` callback in `auth.ts` bypasses password validation for recovery-code sign-ins (`__recovery__` flag).

## tRPC

- Router root at `apps/web/src/server/api/root.ts`
- Context: `createTRPCContext()` calls `auth()` to get session + `getDatabaseClient()` for DB
- `publicProcedure` -- no auth required
- `protectedProcedure` -- requires valid session, provides `ctx.session.user.id`
- For server components: use `appRouter.createCaller(await createTRPCContext())`

## AI Providers

Providers are registered via a singleton `ProviderRegistry` in `packages/ai/src/registry.ts`.

### Implemented providers

| Provider | File                                  | Env var          | Notes                                                        |
| -------- | ------------------------------------- | ---------------- | ------------------------------------------------------------ |
| OpenAI   | `packages/ai/src/providers/openai.ts` | `OPENAI_API_KEY` | Full support (chat, streaming, embeddings, vision)           |
| Groq     | `packages/ai/src/providers/openai.ts` | `GROQ_API_KEY`   | OpenAI-compatible API. Chat + streaming only (no embeddings) |

Both use the same `OpenAICompatibleProvider` class -- no separate code needed for each.
Any OpenAI-compatible API works with `apiKey` + `baseUrl` + `model` in the agent config.

### Adding a new provider

For OpenAI-compatible APIs: just configure the agent in the dashboard with "OpenAI Compatible" type, set the `baseUrl`, `apiKey`, and `model`. No code changes needed.

For non-OpenAI-compatible APIs (e.g., Anthropic): create a provider file implementing `AIProvider`, then register it.

## Agent Knowledge Management

Agent-level document assignment controls which documents each agent can access for RAG retrieval.

### Privacy Model (Whitelist)

- **No `agent_documents` entries** for an agent = agent has workspace-wide access to all documents (shared/public).
- **Entries exist** in `agent_documents` = agent is scoped to only those assigned documents (private).
- This is a whitelist approach: explicitly assign documents to restrict, or leave empty for full access.

### Schema

`agent_documents` junction table (`packages/db/src/schemas/pg/agent-documents.ts` and `sqlite/`):

- `id` (UUID, PK)
- `agentId` (UUID, FK to agents)
- `documentId` (UUID, FK to documents)
- `createdAt` (timestamp)
- Unique constraint on `(agentId, documentId)`

### How It Works

1. **Ingest**: `POST /api/documents/ingest` accepts optional `agentId`. If provided, creates an `agent_documents` entry linking the document to the agent.
2. **Retrieval**: `packages/rag/src/retrieval/index.ts` accepts optional `agentId`. When provided, only chunks from the agent's assigned documents are used for RAG. Falls back to workspace-wide when no `agentId`.
3. **Chat routes**: Both `apps/web/src/app/api/chat/[conversationId]/route.ts` and the public widget chat route pass `agentId` to the RAG retrieval function.
4. **UI**: Agent detail page has a "Knowledge" tab (`KnowledgeTab` component in `agent-detail-client.tsx`) for assigning/unassigning documents and editing knowledge instructions.
5. **Instructions**: `knowledge_instructions` text column on `agents` table stores custom instructions for how the agent uses its knowledge base.

### tRPC Router

`agentKnowledge` router at `apps/web/src/server/api/routers/agent-knowledge.ts`:

- `getAssignedDocuments` — returns documents assigned to a specific agent
- `getWorkspaceDocuments` — returns all workspace docs (for the assign modal)
- `assignDocument` — creates an `agent_documents` entry
- `unassignDocument` — removes an `agent_documents` entry
- `updateInstructions` — updates `knowledge_instructions` on the agent

## Test Conversations

Test conversations let you preview agent behavior without polluting analytics.

### How It Works

1. **Widget**: Appending `?test=true` to the widget URL puts it in test mode. A "TEST" badge appears in the widget header.
2. **Conversation creation**: When `?test=true` is present, new conversations are created with `is_test: true` in the database.
3. **Analytics exclusion**: `packages/analytics/src/service.ts` excludes `is_test=true` conversations from all queries (overview, volume, status distribution, agent ranking, channel distribution).
4. **Dashboard filtering**: Conversations list (`conversations-list.tsx`) has a filter toggle (All / Real only) and shows a "Test" badge on test conversations.
5. **Agent preview**: `/dashboard/agents/[agentId]/preview` renders a mock website with the widget in test mode — lets you test an agent without creating real conversations.

### Schema

`is_test` boolean column on `conversations` table (PG + SQLite), default `false`.

## Widget Preview

The agent preview page at `/dashboard/agents/[agentId]/preview` provides a sandboxed testing environment.

- Server component at `preview/page.tsx` fetches the agent and its widget channel
- Client component at `preview/preview-client.tsx` renders a mock website with the real widget iframe in test mode
- "Preview" button in the agent detail header navigates to the preview page
- All conversations created during preview are marked as test conversations

## Coding Conventions

- **TypeScript**: strict mode throughout
- **Validation**: Zod for runtime validation
- **Schema**: Drizzle + drizzle-zod for insert schemas
- **Commits**: conventional commits (feat:, fix:, chore:, docs:, etc.)
- **No comments** in code -- let the code speak
- **No emoji** in files unless user requests it
- **Style**: Prettier with shared config

## Current State & Gotchas

- **Port 3000**: Kill stale `next-server` with `kill $(lsof -ti:3000)` before starting dev
- **Tailwind v4**: PostCSS pipeline requires `@tailwindcss/postcss` + `postcss.config.mjs`. Both are in place now.
- **Server actions**: Form submissions require `multipart/form-data` encoding. Setup uses JSON-formatted server actions (not form actions).
- **Signup flow**: First user (count === 0) -> `status: "active"` -> auto sign-in -> `redirect("/dashboard")`. Subsequent users -> `status: "pending"` -> `redirect("/pending-approval")`
- **agent-browser**: Requires Chromium: run `agent-browser install` before first use
- **SQLite vs PostgreSQL schemas**: Both maintained separately in `schemas/pg/` and `schemas/sqlite/`. Keep in sync when adding tables.
- **Setup wizard**: Uses server actions in `apps/web/src/lib/actions/setup.ts`. The layout at `(setup)/layout.tsx` has no auth check.
- **First-run detection**: Homepage detects configured state. Signed in → `/dashboard`. User exists → `/signin`. No user → setup prompt.
- **Idle timeout**: `IdleTimeoutProvider` wraps dashboard layout. Configurable in Settings page at `/dashboard/settings`.
- **Page transitions**: Custom `PageLoader` component with morphing ring animation. Loading.tsx files in all route groups.
- **Mobile sidebar**: Collapsible overlay drawer with hamburger button. Access sidebar via Menu icon in header (mobile only).
- **Website crawler**: Full site crawler at `packages/rag/src/crawler/`. Docs page has "Website" tab for URL submission. Async with status polling.
- **Settings page**: `/dashboard/settings` with session timeout toggle, idle timeout (minutes), and max session length (hours) inputs.
- **Signin/signup pages**: Full-bleed layout (no card wrapper), matching homepage visual style with Command icon branding.
- **Theme switching**: Not yet implemented. Tracked in ADR-007.
- **Widget preview**: `/dashboard/agents/[agentId]/preview` renders a mock website with the widget in test mode. "Preview" button in agent detail header.
- **Test conversations**: Widget `?test=true` creates test conversations. Analytics exclude them. Dashboard shows "Test" badge and filter toggle.
- **Agent knowledge**: Whitelist model via `agent_documents` junction table. No entries = workspace-wide access, entries exist = private to those agents. KnowledgeTab in agent detail page.
- **Agent-channel auto-create**: Creating an agent automatically creates a Web Widget channel for it. The setup wizard also creates a channel alongside the agent.
- **Security codes**: Compulsory post-setup prompt for recovery codes. Sign-in form has password/security-code toggle. Recovery sign-in forces password change.

## Deferred

- **Theme switching**: ADR-007 documents the plan. CSS variable approach with `data-theme` attribute + `localStorage` persistence.
- **PostgreSQL guided install in wizard**: Step 2 currently shows TUI config. Future: guided install with OS detection and step-by-step instructions.
- **SQLite migration via Drizzle Kit**: Currently using raw SQL. Could use a second `drizzle.config.sqlite.ts` for proper migration generation.
